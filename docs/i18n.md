# 多语言工作流

本文回答一个问题:给 XID 加或改一句用户可见文案时,该怎么做才不会漏翻译、不会中英混排。读者是要改 UI、SDK 或 Worker 错误消息的贡献者。

XID 使用 Lingui 覆盖 SPA、React SDK 和 Worker 用户可见错误。事务邮件模板不进入 Lingui，按设计使用 Mustache 子集和 R2 语言包，并保留内置 fallback。

## 同步命令

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/extract.sh
```

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/compile.sh
```

严格校验时：

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/compile.sh --strict
```

用户可见 TSX 文案覆盖审计：

```bash
pnpm run i18n:audit
```

浏览器运行时审计：

```bash
pnpm run i18n:runtime
```

该命令默认启动本地 server 验证当前工作树。复核已部署实例时指定 base URL：

```bash
XID_I18N_RUNTIME_BASE_URL=https://<your-domain> pnpm run i18n:runtime
```

它用真实 Chrome 遍历 `/`、`/sign-in`、`/docs`、`/docs/scim` 四个公开入口和全部 locale，验证 `html lang`、页面目标语言文案和 console error。

## 执行顺序

多语言收口不能先按 8 个 `.po` 全量翻译推进。正确顺序是：

1. 先用 `Trans`、`t` 或 runtime descriptor 覆盖用户可见 UI 文案。
2. 再运行 `pnpm run i18n:audit`，确认 TSX 可见文本没有绕过 Lingui，且所有非 source locale 没有空翻译或整句 source 文案直出。
3. 再按 locale 补译 `.po` 并运行 `pnpm exec lingui compile --strict`。
4. 最后用真实浏览器验证关键页面的 `html lang`、对应 `messages.mjs` 加载和页面文案。

如果源码仍有硬编码用户文案，继续翻译 catalog 不能解决中英文混写。新增文案必须先进入 Lingui，再进入 catalog。

## 当前 catalog 状态

- 8 个 locale:en、zh-Hans、ja、ko、fr、de、es、pt-BR。
- 非 source locale 的 `Missing` 为 0,严格编译不依赖空缺 fallback。
- `pnpm run i18n:audit` 是 Vitest gate:`apps/server/src/lib/i18n-ui-audit.test.ts` 覆盖 `apps/server/src` 和 `packages/react/src` 的 TSX 用户可见文本节点、`aria-label`、`alt`、`placeholder`、`title`;`packages/i18n/src/catalog.test.ts` 覆盖各非 source locale catalog 无空翻译、无整句 source 文案直出,并对 zh-Hans、ja、ko 检查目标文字。
- React SDK 已从 `@lingui/react/macro` 迁移到 runtime descriptor,`@lingui/react` 作为 peer dependency 外部化;SDK build 不输出 `babel-plugin-macros` external warning 或 dependency bundling hint。
- React SDK `UserAvatar` fallback `alt` / `aria-label`、SDK 控件文案和 MFA 方法导航 `aria-label` 已纳入 catalog。

单独审计某一种语言不足以阻止其他 locale 中英文混写,统一走 `pnpm run i18n:audit`。

## Email template 语言包

事务邮件不进入 Lingui。Email Queue Consumer 的加载顺序为：

1. `email-templates/<locale>/<type>.json`
2. `email-templates/en/<type>.json`
3. worker 内置模板

worker 内置模板是品牌化 HTML + text fallback,覆盖 `verify_email`、`magic_link`、`otp`、`password_reset`。HTML 使用邮件客户端兼容的 inline style 和 table 布局,包含 XID 文字品牌、标题、说明、CTA、备用链接、过期提示和安全提示；OTP 邮件包含独立验证码块。默认不依赖远程图片,避免首封认证邮件被图片拦截影响关键动作。

R2 JSON 必须包含完整字段：

```json
{
  "subject": "Verify your email",
  "html": "<!doctype html><html><body><p>Use this link:</p><a href=\"{{ link }}\">Verify email</a></body></html>",
  "text": "Use this link: {{ link }}"
}
```

缺少任一字段或 JSON 解析失败时跳过该对象，继续 fallback。全部 fallback 缺失时记录 `template_not_found` 到 `notification_failures`。

首版唯一 email provider 是 Cloudflare Email Service binding `env.EMAIL.send({ from, to, subject, html, text })`。Resend、SendGrid、SMTP 不保留未实现配置路径。

## 新增文案规则

- SPA React UI 使用 `Trans` 或 `t` macro。
- React SDK 使用 runtime descriptor,不从 SDK 包 import `@lingui/react/macro`。
- 新增或修改 TSX 用户可见文案或 locale catalog 后必须跑 `pnpm run i18n:audit`，防止文案绕过 Lingui 或非 source locale 直出英文导致页面中英文混写。
- plural 和变量使用 Lingui ICU。
- Worker 用户可见错误走 i18n runtime，不直接写硬编码英文给终端用户。
- 事务邮件模板不使用 Lingui，使用 Mustache 和 R2 语言包。
