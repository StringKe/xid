# Localization Workflow

This document answers one question: when you add or change a user-visible string in XID, what do you have to do so that nothing goes untranslated and no page ends up mixing English with another language. The reader is a contributor changing the UI, an SDK, or a Worker error message.

XID uses Lingui across the SPA, the React SDK and user-visible Worker errors. Transactional email templates deliberately stay out of Lingui: they use a Mustache subset plus R2 language packs, with a built-in fallback.

## Scope

| Area                           | Tooling                   | Status |
| ------------------------------ | ------------------------- | ------ |
| Hosted UI                      | Lingui macro              | PASS   |
| Platform console               | Lingui macro              | PASS   |
| Account portal                 | Lingui macro              | PASS   |
| React SDK                      | Lingui runtime descriptor | PASS   |
| User-visible Worker API errors | Lingui runtime            | PASS   |
| Email templates                | Mustache + R2             | PASS   |

## Sync commands

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/extract.sh
```

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/compile.sh
```

For strict validation:

```bash
bash .stdai/standards/skills/lingui-i18n/scripts/compile.sh --strict
```

Coverage audit for user-visible TSX strings:

```bash
pnpm run i18n:audit
```

Browser runtime audit:

```bash
pnpm run i18n:runtime
```

By default that command starts a local server and validates the current working tree. To re-check a deployed instance, point it at a base URL:

```bash
XID_I18N_RUNTIME_BASE_URL=https://<your-domain> pnpm run i18n:runtime
```

It drives a real Chrome across four public entry points (`/`, `/sign-in`, `/docs`, `/docs/scim`) in every locale, and validates `html lang`, the target-language copy on the page, and console errors.

## Order of work

Localization cannot be closed out by translating all eight `.po` files first. The correct order is:

1. Cover user-visible UI copy with `Trans`, `t` or a runtime descriptor.
2. Run `pnpm run i18n:audit` and confirm that no visible TSX text bypasses Lingui, and that no non-source locale has an empty translation or a whole source string passed through verbatim.
3. Complete the `.po` translations locale by locale and run `pnpm exec lingui compile --strict`.
4. Finally, use a real browser to verify `html lang`, the matching `messages.mjs` load and the on-page copy for the key pages.

If hardcoded user-facing copy is still in the source, translating more of the catalog will not fix mixed-language pages. New copy must enter Lingui first and the catalog second.

## Current catalog state

- 8 locales: en, zh-Hans, ja, ko, fr, de, es, pt-BR.
- `Missing` is 0 for every non-source locale, so strict compilation does not depend on a fallback for gaps.
- `pnpm run i18n:audit` is a Vitest gate. `apps/server/src/lib/i18n-ui-audit.test.ts` covers user-visible TSX text nodes plus `aria-label`, `alt`, `placeholder` and `title` across `apps/server/src` and `packages/react/src`. `packages/i18n/src/catalog.test.ts` asserts that every non-source catalog has no empty translation and no whole source string passed through, and additionally checks for target-script characters in zh-Hans, ja and ko.
- The React SDK has moved off `@lingui/react/macro` to runtime descriptors, with `@lingui/react` externalized as a peer dependency. The SDK build emits no `babel-plugin-macros` external warning and no dependency bundling hint.
- The React SDK `UserAvatar` fallback `alt` and `aria-label`, the SDK control copy, and the MFA method navigation `aria-label` are all in the catalog.

Auditing a single language is not enough to keep other locales from mixing languages. Always go through `pnpm run i18n:audit`.

## Email template language packs

Transactional email stays out of Lingui. The Email Queue Consumer loads templates in this order:

1. `email-templates/<locale>/<type>.json`
2. `email-templates/en/<type>.json`
3. The worker built-in template

The built-in templates are branded HTML with a text fallback and cover `verify_email`, `magic_link`, `otp` and `password_reset`. The HTML uses email-client-compatible inline styles and table layout, and contains the XID wordmark, a heading, explanatory copy, a CTA, a fallback link, an expiry notice and a security notice; OTP email adds a dedicated code block. Nothing depends on a remote image by default, so a blocked image cannot break the critical action in a user's first authentication email.

An R2 JSON must contain every field:

```json
{
  "subject": "Verify your email",
  "html": "<!doctype html><html><body><p>Use this link:</p><a href=\"{{ link }}\">Verify email</a></body></html>",
  "text": "Use this link: {{ link }}"
}
```

If any field is missing or the JSON fails to parse, that object is skipped and the fallback continues. When every fallback is missing, `template_not_found` is recorded in `notification_failures`.

The only email provider in the first release is the Cloudflare Email Service binding, `env.EMAIL.send({ from, to, subject, html, text })`. No unimplemented configuration path is kept for Resend, SendGrid or SMTP.

## Rules for new copy

- SPA React UI uses the `Trans` or `t` macro.
- The React SDK uses runtime descriptors and never imports `@lingui/react/macro` from the SDK package.
- After adding or changing user-visible TSX copy or a locale catalog, run `pnpm run i18n:audit`. It is what stops copy from bypassing Lingui and stops a non-source locale from emitting English, which is what produces mixed-language pages.
- Plurals and variables use Lingui ICU.
- User-visible Worker errors go through the i18n runtime; never hand hardcoded English to an end user.
- Transactional email templates do not use Lingui. They use Mustache plus R2 language packs.
