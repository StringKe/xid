# API 契约

本文档回答一个问题:XID 的每个 HTTP 端点对外承诺什么形状的请求与响应,以及这个承诺背后有多强的证据。读者是接入 Management API、Hosted Auth 端点或 SCIM 的集成者,以及要改动这些端点的贡献者。

想知道协议层面支持到什么程度看 `docs/protocols/`;想知道 SDK 怎么调看 `docs/sdks/`。

## 状态口径

表格里的状态列有两种含义,不要混淆:

- `PASS` 表示该契约已有实现和对应代码或测试证据,不等于已在真实环境跑通。
- 标注 L4 的条目表示该路径在真实部署环境验证过。

判读规则:

- 只有 mock D1、mock fetch、mock queue、fake provider、fake browser、组件测试或 focused 单测的条目只能算 L1,不得用来宣称生产可用。
- 认证、cookie、route fallback、公开 docs、console、provider、D1、Queues 和部署的完整证据看 `docs/protocols/source-map.md`、`docs/protocols/gap-audit.md` 和 `docs/sdks/platform-matrix.md` 的 L2/L3/L4 列。
- 登录类接口即使单测 PASS,仍必须用真实 Worker HTTP、真实浏览器和真实部署环境验证 cookie 写入后同一 cookie 请求 `/v1/me` 成功。

## 产品语言:Organization 而非 Tenant

公开产品模型是 Instance、Organization、Project、Application、User、Session。`TenantContext`、`tenant_id`、tenant query layer 只是内部 resolver 和数据隔离实现,**不是产品对象**。用户可见 UI、公开 docs、公开 API 文档和 SDK 文档一律用 Organization。

由此产生的几条固定契约:

- 公开路径是 `/v1/platform/organizations` 和 `/scim/v2/organizations/{organization_id}`。`/v1/platform/tenants`、`TenantItem`、`/scim/v2/{tenant_id}` 是历史形态,已删除,请求返回 404。
- `POST /v1/sessions/active-organization` 返回轻量 `ActiveOrganizationResponse`,core SDK 调用成功后重新 `load()` 读取 `/v1/me`。请求 body 必须显式包含 `organizationId` 为 string 或 null,缺字段或非法值返回 422。
- SDK 构造参数不接受 `tenant`,也不发送 `X-Xid-Tenant` header。SDK 只接受 `apiUrl` 作为自托管或自定义域入口覆盖;organization 解析由 Host、OIDC context、identifier resolver、session 和显式 `organizationId` API 完成。

Hosted Auth 策略规则：

- 前端 `GET /auth/config` 只返回可公开字段。
- UI 只展示 `enabled = true` 且允许登录或允许创建的方式；`forceSso` 命中时只展示 enterprise SSO。
- 前端 passkey Conditional UI 也必须受同一策略 gate 控制。`/auth/config` 未启用 passkey 时,登录页不得自动请求 `/auth/passkey/challenge`。
- 未配置或禁用的 social provider 不出现在 `socialProviders`。
- Worker 端对 password、magic link、email OTP、WhatsApp OTP、SMS OTP、passkey、social authorize/callback 再做策略校验。
- Worker 端策略拒绝统一写入 `AUDIT_QUEUE`，事件名 `auth.policy_denied`。payload 包含 `method`、`action`、`reason`、`path`、`ip`、`identifierType`、`identifierHash`、`emailDomain` 和可选 `provider`；不得写入完整邮箱、手机号或 OTP code 明文。
- Email、WhatsApp、SMS consumer 成功发送后写入 `AUDIT_QUEUE`，事件名 `notification.sent`。payload 包含 `channel`、`type`、`provider`、`recipientType`、`recipientHash`、`emailDomain`；不得写入完整邮箱、手机号、token 或 OTP code 明文。provider 发送失败按 `notification_failures` 记录,但 `recipient` 只存 `sha256:<hash>`,`payload` 只存 channel、type、tenantId、orgId、userId、locale、purpose、action、expiresInMin、recipientType、recipientHash、emailDomain 等非秘密字段,不得写入完整邮箱、手机号、link、token、code 或消息正文。
- Password 统一端点按 identifier 是否已存在区分 `login` 和 `user_creation`。已有用户必须满足 `password.allowLogin`；新用户必须满足 `password.allowUserCreation`，并执行 identifier mode、域名、密码长度和 HIBP 检查。
- Social callback 对新用户创建必须检查 `allowUserCreation`、`requireVerifiedEmail`、`allowedEmailDomains`、`blockedEmailDomains`。
- Magic Link 发送端按邮箱是否已存在区分 `login` 和 `user_creation`。已有用户必须满足 `magicLink.allowLogin`，新用户必须满足 `magicLink.allowUserCreation`；策略拒绝仍返回枚举防护成功响应且不发信。
- Magic Link JWT 带 `action = login | user_creation`，验证端消费 token 后重新按 action 复验策略，并把主邮箱标记为 verified。
- Email OTP 发送端按邮箱是否已存在区分 `login` 和 `user_creation`。已有用户必须满足 `emailOtp.allowLogin`，新用户必须满足 `emailOtp.allowUserCreation`；策略拒绝仍返回枚举防护成功响应且不发码。
- Email OTP 验证成功后删除一次性 token、把主邮箱标记为 verified，并签发 session。
- `forceSso = true` 且 enterprise SSO `enabled + allowLogin + domainDiscovery` 时，Hosted UI 只展示企业 SSO 邮箱发现表单。
- `POST /sso/hrd` 只在 enterprise SSO `enabled + allowLogin + domainDiscovery` 时查询 verified org domain，并同时执行 Hosted Auth 全局 `allowedEmailDomains` / `blockedEmailDomains` 和 enterprise SSO `allowedEmailDomains` / `blockedEmailDomains`；企业 SSO 或域名发现被策略拒绝时返回 `{ connectionId: null }` 并写 `auth.policy_denied`。
- OIDC RP JIT 和 SAML JIT 同时执行 Hosted Auth 全局 domain 策略与 enterprise SSO domain 策略。任一策略拒绝时不创建用户、不同步已有用户、不写 membership。
- `/sign-up` 进入统一 `/sign-in?intent=sign-up`，不显示固定 email + password 注册表单；不存在独立 `POST /auth/sign-up` API。

## Platform console

认证方式：cookie session。权限要求：`manager_assignments.manager_role = instance_manager` 且 `scope_type = instance`。

`GET /v1/me` 的 `user.instanceManager` 字段只用于同源 console 守卫。该字段来自平台层 `manager_assignments` 查询，不写入业务 token claim。

`GET /v1/me` 的 `organizations[].role` 来自 membership;持有 `manager_assignments.manager_role = org_manager`(scope_type = org)的用户,member 提升为 `admin` 返回,无 membership 的受管 org 也会以 `admin` 补登进列表,与 `requireOrgManager` 的放行语义对齐。

平台视图主入口在统一 console 下：`/console/platform`、`/console/platform/organizations`、`/console/platform/users`、`/console/platform/events`、`/console/platform/flags`、`/console/platform/billing`。`/platform-admin/*` 不再注册为兼容入口，不承载独立 admin SPA。旧 `/v1/platform/tenants` 已删除并返回 404,公开 docs、SDK 和 catalog 不再引用旧命名。

## Management API

认证方式：`Bearer sk_live_*` 或 `Bearer sk_test_*`。租户隔离：`TenantContext` + `createTenantDb`。API key scope 规则：

- `scopes = []`：无权限。写操作和读操作均必须匹配显式 scope。
- `resource:read`：允许对应资源 GET / export 类读操作。
- `resource:write`：允许对应资源 POST / PATCH / PUT / DELETE / revoke / rotate 类写操作。
- `resource:*`：允许对应资源读写。
- `*`：允许全部 Management API 资源。
- 认证成功但 scope 不足返回 `403` 和 `code = insufficient_permission`。

## 错误契约

`/introspect`、`/revoke`、`/device_authorization`、`/register` 四个 OAuth 协议端点的错误响应是 RFC 形状 `{error, error_description}`，由端点内直接构造，不经全局 onError。它们不返回 XidAPIError `{code, message}`。

错误形状按端点族分流：

- 协议端点(RFC 族)：`/authorize`、`/token`、`/userinfo`、`/introspect`、`/revoke`、`/device_authorization`、`/register`、`/par`、`/backchannel_authentication`、`/end_session` 等 OIDC/OAuth 端点，错误为 `{error, error_description}`(RFC6749 5.2 及各 RFC 扩展码)。client 认证失败 401 带 `WWW-Authenticate`(Basic client：`Basic realm="xid", error="invalid_client"`；DCR 管理端 RAT：`Bearer realm="xid", error="invalid_client"`)；`/register` 使用 RFC7591 规范码 `invalid_redirect_uri` / `invalid_client_metadata` / `invalid_software_statement`。
- Management API 与 Hosted UI 端点(`/v1/**`、`/auth/**`)：错误为 XidAPIError `{code, message, meta?}`，即以下各条。
- SCIM 端点(`/scim/**`)：错误为 scimError 形状(`application/scim+json`)，未匹配路径的 404 同形状。

- 边界错误统一使用 `AppError`。
- cookie session 缺失返回 `401` 和 `code = unauthorized`。
- platform 权限不足返回 `403` 和 `code = forbidden`。
- 资源不存在返回 `404`，不可泄露跨租户资源存在性。
- 输入字段错误返回 `422` 和 `code = validation_failed`，需要带 `meta.paramName` 时应明确字段名。
